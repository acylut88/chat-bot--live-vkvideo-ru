# Стандарты разработки проекта «Танковый Синдикат»

## 1. Архитектурные принципы
*   **OOP (Объектно-ориентированное программирование):** Вся бизнес-логика инкапсулируется в классы-сервисы. Никаких «голых» глобальных функций.
*   **DRY (Don't Repeat Yourself):** Повторяющийся код, формулы или логика выносятся в базовые классы, утилиты или конфигурационные структуры.
*   **Чистая архитектура (Separation of Concerns):** Конфигурация, базы данных, внешние API (VK, Lesta) и бизнес-логика живут в строго изолированных модулях.

## 2. Управление конфигурацией
*   Запрещено хардкодить любые настройки, шансы, награды, URL-адреса, ID или токены в файлах логики.
*   Все конфигурационные файлы реализуются строго через библиотеку `pydantic-settings` (класс `BaseSettings`) с поддержкой автоматического чтения `.env` файла.

## 3. Структура проекта и корень репозитория
*   В корне проекта разрешено находиться только **одному** Python-файлу — точке входа `main.py`.
*   Вся остальная кодовая база распределяется по изолированным логическим пакетам внутри директории `src/`:
    *   `src/core/` — Глобальные системные настройки, конфиги и инициализация (база данных, сессии).
    *   `src/models/` — Описание декларативных схем данных и таблиц БД.
    *   `src/services/` — Бизнес-логика, калькуляторы и математические движки.
    *   `src/workers/` — Асинхронные фоновые процессы (парсеры чата, слушатели API).
*   Тесты изолируются в отдельную корневую директорию `tests/`.

## 4. Правила игровой экономики и Лутбоксов
*   Бот работает по принципу "Процессингового центра": валидация лимитов, цен и КД лежит на VK Видео. Бот обрабатывает каждое пришедшее событие как легитимное.
*   Прогресс прохождения цепочки лутбокса является атомарным (все 6 шагов до первого взрыва просчитываются целиком за один клик по награде).
*   Математическое ядро должно поддерживать три режима агрегации наград за стрим: `ABSOLUTE_MAX`, `TOTAL_ACCUMULATIVE`, `STEP_ACCUMULATIVE`. Модификаторы тиров коробок и VIP-статусы влияют как на количество лута, так и на шансы кубика.

## 5. Проектирование Базы Данных (SQLAlchemy 2.0)
*   Описание моделей таблиц ведется строго в современном декларативном стиле SQLAlchemy 2.0 с использованием конструкций `Mapped[...]` и `mapped_column()` для обеспечения строгой типизации.
*   Все штампы времени и даты (`DateTime`) записываются в базу данных строго в формате **UTC** (`datetime.datetime.utcnow`). Конвертация под локальные часовые пояса стримеров происходит на уровне клиента.
*   Для обеспечения SaaS-изоляции данных между таблицами стримеров и логами/балансами пользователей настраивается жесткое каскадное удаление (`cascade="all, delete-orphan"`).

## 6. Процесс выполнения задач (Definition of Done)
Перед тем как сделать коммит и закрыть задачу, разработчик обязан:
1.  Написать изолированный тестовый скрипт / симуляцию в папке `tests/`.
2.  Запустить тесты локально и убедиться в отсутствии ошибок.
3.  Зафиксировать успешные результаты тестов (логи/вывод) в описании закрытия задачи.

## 7. Требования к коммитам и Git-Flow
*   Использовать стандарт Conventional Commits (`feat(...)`, `fix(...)`, `chore(...)`, `test(...)`).
*   Каждому коммиту должен предшествовать код задачи из Jira (например, `feat(logic): TS-1 ...`).
*   Запрещено делать прямые мержи в ветку `main` локально. Слияние фича-веток происходит через создание Pull Request на GitHub.
